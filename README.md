# Treatment-Recommendation--App
Instructions To Run App:
First open the program and install the required package by typing install.packages("shiny") in the Console if you haven’t already. Utilize RStudio. Then create a new R script (File → New File → R Script), copy and paste the full Shiny app code for your CVD project into the script, making sure it includes the library(shiny) line along with the ui, server, and shinyApp(ui = ui, server = server) parts. After pasting the code, either click the “Run App” button at the top of the script window or run the app line manually in the Console. If everything is set up correctly, a popup window or the Viewer pane will open showing your full interactive app. If no popup appears, check for errors in the Console and confirm that all required packages are installed and loaded.

About:
The README opens with a brief overview explaining that CVD Analytica is a single-file R Shiny application that combines clinical risk modelling with a Google Gemini-powered AI assistant to deliver personalised cardiovascular health insights. It notes that despite living in one file, the code is internally divided into eight clearly labelled sections: configuration and constants, the API client, clinical calculators, AI content generators, SVG renderers, CSS and JavaScript assets, the UI definition, and the server logic. Each section is separated by a prominent comment banner so any developer can jump directly to the relevant part without reading the entire file.

The README then describes the nine application tabs and what each one does. The Patient tab collects demographics and vitals and runs the risk analysis. The Dataset tab lets users upload and explore a CSV file. The Models tab trains three machine learning classifiers and displays ROC curves and AUC scores. The AI Chat tab provides a conversational health assistant with voice input and text-to-speech output. The AI Plans tab generates a personalised recommendations list, a seven-day meal plan, a four-week exercise programme, and medication education. The Sentiment tab analyses the emotional tone of AI-generated content. The Story tab produces an empathetic narrative about the patient's health journey. The Report tab assembles everything into a downloadable PDF. The Feedback tab presents an AI-generated post-session questionnaire.

The libraries section lists every R package and explains its role in plain terms. Shiny provides the web framework. shinyjs bridges R and JavaScript. caret handles the train/test split and confusion matrices. DT renders interactive data tables. randomForest and xgboost provide the two ensemble classifiers. pROC computes ROC curves and AUC scores. jsonlite and httr together handle the JSON payload construction and HTTP communication with the Gemini API. ggplot2 draws all static plots. sentimentr scores sentence-level sentiment in the chat log. syuzhet applies the NRC emotion lexicon to AI-generated text. rmarkdown renders the downloadable PDF reports. reshape2 melts the correlation matrix into a plottable long format. On the frontend, Chart.js is loaded from a CDN to draw the animated AUC comparison bar chart, and the browser's native Web Speech API handles voice input and text-to-speech output.

The dataset section explains that the app expects a semicolon-delimited CSV where age is stored in days and is converted to years on load, and it directs the user to the Cardiovascular Disease dataset on Kaggle which matches the required schema exactly.

The setup instructions walk through installing R, running a single install.packages call with all fourteen dependencies, optionally installing tinytex for PDF export, replacing the hardcoded API key with a valid Gemini key from Google AI Studio, and launching the app with shiny::runApp. A note at the end advises loading the key from an environment variable rather than hardcoding it before any shared or production deployment.

Modular Design

Rather than placing all logic directly inside Shiny's server function, each concern is extracted into its own named function at the top of the file. The Gemini API communication is entirely contained within a single call_gemini_api function that accepts a prompt and a key and returns a consistent named list. Every AI generation task — recommendations, meal plans, exercise plans, stories, medication info, tone analysis, and feedback questions — calls that one function through its own thin wrapper that only supplies the domain-specific prompt text. The clinical mathematics are similarly isolated: compute_bmi, compute_framingham_score, flag_hypertension, and flag_diabetes each do exactly one thing and can be read, tested, or changed without touching anything else. The three SVG renderers are standalone functions that accept data values and return SVG strings, keeping all presentation logic out of the server body. This separation means that changing the Gemini model endpoint, adjusting a clinical threshold, or redesigning the gauge graphic each require editing exactly one function with no side effects elsewhere.

Meaningful Naming

Every identifier is named to convey its purpose at a glance. The reactive value that holds the patient's predicted probability is called rv_cvd_probability rather than the original rv_prob. The training and test sets are called train_set and test_set rather than tr and te. Predicted probability vectors are named predicted_probs_logreg, predicted_probs_rf, and predicted_probs_xgb rather than p_lr, p_rf, and p_xgb. The flag functions are named flag_hypertension and flag_diabetes to make it clear they return a categorical flag, not a continuous score. Risk band helper functions use the full words risk_label, risk_colour, and risk_class rather than riskLabel, riskColor, and riskClass, and they follow R's conventional snake_case style throughout. Constants like RISK_HIGH_THRESHOLD and RISK_MODERATE_THRESHOLD are named in uppercase to signal that they are configuration values and are defined once at the top of the file so the thresholds never appear as unexplained magic numbers buried inside conditionals.

Consistent Formatting

All code uses two-space indentation throughout, matching the R community convention. Function arguments that span multiple lines are vertically aligned so the structure is immediately scannable. Binary operators are surrounded by single spaces on both sides. Long prompt strings are broken across multiple lines with clear concatenation rather than being written as one unreadable string. Comment banners use a uniform style: a row of equals signs and a section number for major divisions, and a row of hyphens for subsections within the server. This means the visual hierarchy of the file mirrors the logical hierarchy of the application.

Appropriate Comments

Every function carries a header comment that states what it does, describes each parameter with its type and meaning, and documents the return value, following the Roxygen2 documentation convention used across the R ecosystem. Inside longer functions, inline comments explain non-obvious decisions such as why the Framingham coefficients differ by sex, why the ECG amplitude is calculated the way it is, and why certain reactive values are initialised outside observers. The constants block at the top of the file includes a note explaining that the API key should be loaded from an environment variable in any production deployment. Section banners make it possible to navigate the file without an IDE, and subsection labels within the server divide the observer and render logic into the same eight groups used in the README so that the documentation and the code always describe the same structure.
